# 規格書架構說明

**用途**：說明本專案規格書的分層邏輯、各層邊界與依賴規則，供後續 AI 協作時作為上下文。

---

## 一、目錄結構

```
規格書/
├── Common/                        ← 平台層（專案無關）— 一個 git repo
│   ├── UI/
│   │   ├── UI Foundation Spec/   ← 語言無關 × 專案無關
│   │   └── WPF UI Spec/          ← 語言相關 × 專案無關
│   └── Implementation/
│       ├── Core Contract/        ← 語言無關 × 專案無關
│       ├── Core Implementation/  ← 語言相關 × 專案無關（Core C#）
│       └── WPF Implementation/   ← 語言相關 × 專案無關（UI 實作）
│
├── Projects/
│   └── {專案名}/                  ← 專案層（換專案時整個替換）— 一個 git repo
│       ├── UI/
│       │   ├── Project UI Spec/  ← 語言無關 × 專案相關
│       │   └── Project WPF UI Spec/ ← 語言相關 × 專案相關
│       └── Implementation/
│           ├── Flow Spec/        ← 語言無關 × 專案相關
│           └── Project Implementation/ ← 語言相關 × 專案相關
│
└── 架構決策.md
```

**Git 策略**：本目錄為一個 monorepo，推送至 `https://github.com/HaoTang0611/Spec.git`。新增專案只需在 `Projects/` 下建立新資料夾。

## 二、兩個正交維度

所有規格書文件沿兩條軸分類，互相獨立：

**語言軸**：文件是否依賴特定程式語言或框架
- 語言無關：任何語言實作者都能直接讀懂，不含語法與框架慣例
- 語言相關：針對特定語言（C#）或框架（WPF）撰寫，含技術語意

**專案軸**：文件是否可跨專案複用
- 專案無關：通用，任何使用此平台的專案都能套用
- 專案相關：本專案特有，換專案時整個替換

### UI Branch 四象限

路徑對應：專案無關欄位於 `Common/UI/`；專案相關欄位於 `Projects/<專案資料夾名稱>/UI/`（每個專案各有一個以專案命名的子資料夾，例如 `Projects/測包機/`）。

|  | 專案無關 | 專案相關 |
|--|---------|---------|
| **語言無關** | UI Foundation Spec | Project UI Spec |
| **語言相關** | WPF UI Spec | Project WPF UI Spec |

### Implementation Branch 四象限

路徑對應：專案無關欄位於 `Common/Implementation/`；專案相關欄位於 `Projects/<專案資料夾名稱>/Implementation/`。

|  | 專案無關 | 專案相關 |
|--|---------|---------|
| **語言無關** | Core Contract | Flow Spec |
| **語言相關** | Core Implementation + WPF Implementation | Project Implementation |

語言相關×專案無關格含兩個資料夾，因 Core（硬體/資料/演算法）與 UI 實作（ViewModel/Binding）性質不同，獨立管理但同屬一個象限。

## 三、依賴規則

依賴方向固定，不得反向。箭頭讀作「被依賴」（A → B 表示 B 依賴 A）。

### UI Branch

```
              專案無關                    專案相關
         ┌─────────────┐            ┌──────────────────┐
語言無關 │UI Foundation│───────────→│ Project UI Spec  │
         │    Spec     │            │                  │
         └──────┬──────┘            └────────┬─────────┘
                │                            │
                ↓                            ↓
         ┌─────────────┐            ┌──────────────────┐
語言相關 │ WPF UI Spec │───────────→│Project WPF UI    │
         │             │            │Spec              │
         └─────────────┘            └──────────────────┘
```

### Implementation Branch

```
              專案無關                      專案相關
         ┌──────────────────┐          ┌──────────────────────┐
語言無關 │  Core Contract   │─────────→│     Flow Spec        │
         └────────┬─────────┘          └───────────┬──────────┘
                  │                                │
                  ↓                                ↓
         ┌──────────────────┐          ┌──────────────────────┐
語言相關 │Core Implementation│─────────→│Project Implementation│
         │WPF Implementation│          └──────────────────────┘
         └──────────────────┘
```

### 跨 Branch 依賴（Implementation → UI）

```
WPF Implementation ───→ WPF UI Spec     （實作 WPF 需求）
Flow Spec          ───→ Project UI Spec （專案流程依據專案需求）
```

**隔離原則**：上游文件不得知曉下游文件的存在。UI Foundation Spec 標記「由外部輸入資料決定」，Project UI Spec 自行宣告補充位置。

## 四、兩個 Branch 的定位

### UI Branch
描述「要做什麼」——畫面行為、使用者互動、UI 狀態、視覺規範。不含任何實作細節，不描述資料來源或業務邏輯。

- **UI Foundation Spec**：平台無關的 UI 行為需求，換語言或框架時保留不動
- **WPF UI Spec**：UI Foundation Spec 在 WPF 環境下的補充（分層責任、狀態映射、命名契約），不新增功能
- **Project UI Spec**：本專案特有的 UI 配置（填入 UI Foundation Spec 的插槽），語言無關
- **Project WPF UI Spec**：本專案特有且 WPF 特有的補充，上述三份均未涵蓋的交集部分

### Implementation Branch
描述「怎麼做」——介面契約、資料定義、技術規範、業務流程。語言相關層允許語言語意；Core Contract 為例外，維持語言無關。

- **Core Contract**：跨平台共用的介面契約、資料模型、配置選項、枚舉與狀態、錯誤語意（ICamera、InspectionResult、IProjectProvider 等），語言無關 × 專案無關
- **Core Implementation**：Core Interface 的 C# 實作規範（硬體驅動、AI 推論、影像前處理演算法）
- **WPF Implementation**：ViewModel 配置、Binding 契約、Command 定義（對接 WPF UI Spec 需求與 Core 資料）
- **Flow Spec**：本專案業務流程的語言無關描述（WorkOrder 序列、狀態轉移、觸發條件）
- **Project Implementation**：Flow Spec 的 C# 實作規範

## 五、uc/ 與 components/ 的邊界（UI Branch 內部）

### UC 放什麼
- 使用者的目標與流程
- 畫面的組裝方式（引用哪些 components、排列順序）
- 狀態轉換流程

### components/ 放什麼
- UI 元件的外觀、內部狀態、互動行為
- 不含「為什麼在這裡」的脈絡，只含「這個元件本身怎麼運作」

### 提取到 components/ 的條件（三個都要成立）
1. 出現在超過一個地方
2. 有足夠的內部複雜度（有自己的狀態和互動邏輯）
3. 可以獨立描述（不需要知道「誰用它、為什麼用」）

等到第二個使用者出現時再提取，避免產生「假設中的通用元件」。

## 六、關鍵設計原則

1. **插槽機制**：UI Foundation Spec 標記「由外部輸入資料決定」，Project UI Spec 填入具體值；Core Contract 定義 `IProjectConfiguration`，Project Implementation 實作它。上游保持通用，下游透過填槽擴展。

2. **可抽換性**：
   - 換語言（WPF → Qt）：替換語言相關欄（WPF UI Spec、Project WPF UI Spec、Core Implementation、WPF Implementation、Project Implementation），保留語言無關欄
   - 換專案：在 `Projects/` 下新增專案資料夾並建立新 repo，保留 `Common/` 不動

3. **不重複定義**：每份文件只補充上游未定義的部分。WPF UI Spec 不重寫 UI Foundation Spec，Project UI Spec 不重寫 components/，實作規範不重寫 UI Foundation/WPF UI Spec。

4. **晉升路徑**：下游文件中重複出現的內容，應晉升至對應上游文件，不需要一開始就預測所有可能。
