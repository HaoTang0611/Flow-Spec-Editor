# Flow Spec — 建立計畫

## 問題陳述

Core Contract 已定義完整的介面能力與資料模型，但本專案尚未有任何 Flow Spec 輸出。需要依據本專案業務場景，逐步建立語言無關的業務流程規格，讓下游（Project Implementation、Builder AI、工程師）有明確的流程依據。

---

## 建立原則

1. **只補充業務流程**：不重複描述 Core Contract 已定義的介面語意與資料格式，只描述本專案的觸發條件、序列與狀態轉移。
2. **語言無關**：所有描述必須任何語言實作者都能讀懂，不含語法或框架語意。
3. **可追溯**：每個流程步驟必須能對應到 Core Contract 的介面或操作。
4. **不超前實作**：未確認的業務場景先列為 Open Question，不直接寫入正式規格。
5. **邊界優先**：建立文件前先釐清責任邊界，避免把 Core Contract 或 Project Implementation 的責任寫進來。

## 建議章節結構

每份 Flow Spec 文件 SHOULD 包含：

1. **流程定位**：本文件描述哪個業務場景，依賴哪些 Core Contract 介面
2. **狀態定義**（若有）：業務層的狀態名稱與語意
3. **狀態轉移表**或**流程序列**：前置狀態、觸發條件、後繼狀態與副作用
4. **觸發條件說明**：使用者操作、系統事件、裝置事件的觸發條件
5. **錯誤流程**（若有）：例外情況與業務回應策略
6. **邊界規則**：明確標記哪些責任屬於本層、哪些屬於上游或下游

- 下游可依 Phase 1 文件理解系統從啟動到就緒的完整過程
