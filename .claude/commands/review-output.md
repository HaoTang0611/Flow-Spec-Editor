## 審查範圍

審查只針對正式輸出區：`Flow Spec/`。

本 command 中的「全部文件」一律表示「正式輸出區下的全部 .md 文件」，不是整個 repo 的全部文件。

請選擇：
1. 未提交文件（從 git 找出變更的 .md）
2. 全部文件（`Flow Spec/` 下所有 .md）
或直接輸入指定文件名稱。

啟動 command 後必須先詢問使用者要審查哪個範圍，並等待使用者回答。不得預設選 1，也不得因為存在 git 變更就自行只審查未提交文件。

根據回答：
- 選 1：執行 `git diff --name-only` 與 `git status --short`，只篩出 `Flow Spec/` 下變更的 .md；包含 untracked 文件；如果目前不是 git repo，改請使用者選 2 或指定文件
- 選 2：列出 `Flow Spec/` 下所有 .md（含子目錄），不得掃描正式輸出區以外的文件
- 輸入檔名：只在 `Flow Spec/` 下定位該檔；找不到則報錯；若有重名，列出候選路徑請使用者選擇

## 審查面向

### 面向 A：隔離原則

核心問題：正式輸出中是否混入了「不應該被下游看到」的編輯者工作產物，或重複了下游已持有的上游定義？

檢查項目：

**A1：工作層內容混入**
- 文件中是否出現 Open Questions 清單（問句列表、待確認事項、「待釐清」「TBD」標記）？
- 文件中是否出現 TODO 項目（「TODO:」「待完成」「待補」等標記）？
- 文件中是否出現概念盤點草稿（以分析語氣列出概念清單但未整理成規格格式）？
- 文件中是否出現編輯者工作計畫或進度說明（「本文件目前進度」「下一步」「Phase N」等）？

**A2：本地路徑洩漏**
- 文件中是否出現 `Read Only/`、`Read Only` 或任何相對路徑形式的本地資料夾名稱？
- 若需說明上游依賴或權威來源，MUST 使用「Core Contract」或「架構說明」，或指定具體文件名稱（如 `IInspector`、`WorkOrder`）。

**A3：重複描述上游已定義內容**
- 文件中是否重新解釋 Core Contract 的介面語意（例如說明某個方法的參數型別、回傳語意、已在上游定義的前置條件）？
- 文件中是否重複說明架構說明已定義的分層規則（例如 Flow Spec 的定位、Core Contract 的職責範圍）？
- Flow Spec 應只補充業務流程層面的規範，不重述上游已完整說明的內容。

### 面向 B：邊界

核心問題：正式輸出中是否帶入了不屬於 Flow Spec 這一層的責任？

檢查項目：

**B1：程式語言語法或型別名稱**
- 文件中是否出現任何程式語言語法：C# code block、`async/await`、`Task<T>`、`List<T>`、`Dictionary<K,V>`、Lambda 表達式、LINQ 等？
- 文件中是否出現語言特有型別名稱（`string`、`bool`、`int`、`Guid` 等），而非以業務語言描述？

**B2：WPF / MVVM 實作細節**
- 文件中是否出現 WPF/MVVM 專有概念：`ViewModel`、`Binding`、`Command`、`ICommand`、`CommandParameter`、`Dispatcher`、`XAML`、`INotifyPropertyChanged`、`RelayCommand`、`ObservableCollection`？
- 文件中是否出現 UI 事件（`Click`、`Loaded`、`SelectionChanged`）而非以業務觸發條件描述？

**B3：Project Implementation Orchestration 細節**
- 文件中是否描述具體的類別組合方式、相依注入配置、Service Locator 使用方式？
- 文件中是否說明跨服務的呼叫順序而非業務流程序列？（業務流程序列應描述「做什麼」，不是「哪個類別呼叫哪個類別」）

**B4：未授權的新概念直接寫入規格**
- 文件中是否出現在 Core Contract 中找不到對應定義的新狀態、新操作介面或新資料型別，且未標記為 Contract Gap Proposal？
- 若有新概念，MUST 以「Contract Gap Proposal」區塊標記，並說明是建議修改而非既有契約；任何未標記的新增都視為邊界違規。

**B5：平台通用邏輯（應晉升至 Core Contract）**
- 文件中是否定義了任何適用於所有使用同一平台之專案的通用邏輯，而非本專案特有的業務流程？此類內容不屬於 Flow Spec，應列為 Contract Gap Proposal 或 Open Question。

### 面向 C：跨文件一致性

核心問題：多份文件在術語、格式與約束語使用上是否一致？

檢查項目：

**C1：業務術語一致性**
- 同一個業務概念在不同文件中是否使用相同名稱（例如：「WorkOrder」vs「工單」、「Inspection」vs「檢測」、「AlarmHandling」vs「警報處理」）？混用中英文術語指稱同一概念需標記。
- 同一個業務狀態名稱在不同文件中是否一致（例如：不同文件的狀態轉移表中，若某狀態被多份文件引用，名稱必須完全相同）？

**C2：Core Contract 名稱引用一致性**
- 跨文件引用同一 Core Contract 介面或型別時，名稱拼寫是否完全一致（例如 `IInspector`、`WorkOrder`、`AlarmEvent`）？

**C3：約束語使用一致性**
- MUST / MUST NOT / SHOULD / SHOULD NOT / MAY 是否只用於表達強制或建議約束，不用於描述性說明？
- 強制要求是否一律使用 MUST / MUST NOT，建議是否使用 SHOULD，選用是否使用 MAY？有沒有用「應該」「需要」等自然語言替代 MUST 而意義不清的情況？

**C4：狀態轉移表格式一致性**
- 各文件中的狀態轉移表是否採用一致的欄位格式？CLAUDE.md 指定的欄位為：前置狀態、觸發條件、後繼狀態、副作用。
- 欄位名稱與順序是否跨文件一致？

### 面向 D：缺漏

核心問題：應該有的內容有沒有遺漏？

檢查項目：

**D1：索引同步**
- `Flow Spec/00_index.md` 中列出的所有文件，是否在 `Flow Spec/` 下都能找到對應檔案？
- `Flow Spec/` 下存在的所有 .md 文件（含子目錄），是否都有在 `00_index.md` 中列出入口？
- 若有文件存在於 `Flow Spec/` 但未列入索引，或索引列出但找不到檔案，各自標記為 [Error]。

**D2：必要區段缺漏**
- 每份流程文件 SHOULD 包含以下區段，缺少任一項目標記為 [Warning]：
  - 流程定位（描述哪個業務場景，依賴哪些 Core Contract 介面）
  - 狀態轉移表或流程序列
  - 觸發條件說明
  - 邊界規則
- 「狀態定義」與「錯誤流程」為「若有」條件：若文件定義了多個狀態但缺少狀態定義區段、或定義了狀態轉移但完全未提及錯誤流程，標記為 [Warning]。

**D3：觸發條件可追溯性**
- 文件中定義的每個觸發條件，是否能對應到 Core Contract 的介面操作或事件？若觸發條件無法在 Core Contract 中找到對應依據，且未標記為 Contract Gap Proposal，標記為 [Warning]。

**D4：錯誤流程配對**
- 若文件定義了可能失敗的操作（如裝置呼叫、外部系統互動），是否有對應的錯誤流程或明確說明「錯誤由上游處理，此層不需定義」？缺少對應說明標記為 [Warning]。

### 面向 E：過度設計

核心問題：正式輸出是否超出 Core Contract 授權範圍，自行預留彈性或擴充？

檢查項目：

**E1：未授權的擴充點**

**E2：假設未來需求的設計**
- 文件中是否為假設的未來需求預先定義流程分支或可選路徑，而非目前業務場景實際需要的規格？

**E3：引入不必要的抽象層**
- 文件中是否引入 Core Contract 未定義、且目前業務場景不需要的中間抽象（例如：自行定義「流程管理器」「狀態機介面」等概念，但 Core Contract 未要求）？
